## BETTERBUCKS CURRENCY — CRITICAL ARCHITECTURE NOTE

BetterBucks is a fully internal, closed-loop virtual currency. It is NOT connected to any real-world monetary system, payment processor, or fiat currency at any layer of the application.

- There is NO Stripe integration, NO Apple Pay fiat processing, NO Google Pay fiat processing
- BetterBucks are awarded by orgs to employees entirely within the platform — no money changes hands
- Apple Pay and Google Pay are used ONLY as the tap-gesture UX mechanism to trigger BetterBucks transfers between internal wallets. The native wallet sheet (Apple Pay / Google Pay) is invoked purely for the tap interaction and biometric confirmation (Face ID / fingerprint). Zero dollar amounts are passed; no payment intent is created; no card is charged
- When a user taps via Apple Pay or Google Pay, the result is: sender's BetterBucks wallet balance decreases, recipient's BetterBucks wallet balance increases — this is a pure internal database transaction
- The Apple/Google wallet tap is a UX affordance only — it provides the familiar "hold to pay" gesture and device authentication, then triggers a signed internal API call to transfer BetterBucks between wallets
- Display all balances and transaction amounts in BetterBucks (BB) units only, e.g. "BB 250" — never display dollar signs or fiat equivalents anywhere in the UI
- There is no concept of purchasing, topping up, or cashing out BetterBucks with real money in this application

Implementation of tap-to-transfer:
- Use the Web Authentication API (WebAuthn) or the Payment Request API with a $0.00 amount purely to trigger biometric confirmation on the device
- On successful biometric confirmation, call the internal /api/transfer endpoint with: sender_id, recipient_id, amount (in BB), memo
- The backend validates the transfer (sufficient balance, both users in same org, active accounts), executes the wallet debit/credit atomically in PostgreSQL, and returns a signed transaction receipt
- Never instantiate a Stripe PaymentIntent or contact any external payment API

## TECH STACK

- Frontend: React + TypeScript + Vite (PWA with vite-plugin-pwa)
- Backend: Node.js + Express + TypeScript
- Database: PostgreSQL with Prisma ORM
- Auth: JWT with refresh tokens + role-based access (admin, org, employee)
- Tap-to-Transfer: Payment Request API ($0.00) or WebAuthn for biometric confirmation only — no fiat processing
- Push Notifications: Web Push (service worker)
- Deployment: Configured for replit.app subdomain with environment variables

## ROLES & PORTALS

There are three user roles. Each has its own mobile UI flow:

### 1. ADMIN (Better Bucks Super Admin)
- Login → Admin Mobile Dashboard
- Manage all organizations (create, suspend, view)
- View platform-wide analytics (total BetterBucks in circulation, transaction volume, active users)
- Approve/reject org onboarding requests
- Manage BetterBucks currency supply (mint BB to orgs, burn BB from orgs)
- View all wallet tap transactions across the platform

### 2. ORG (Employer / Organization Account)
- Login → Org Mobile Dashboard
- Manage employees (invite, deactivate, view BB balances)
- Allocate BetterBucks to employees directly from the org's BB pool
- Set redemption rules (which reward catalog items employees can redeem BB for)
- View org-level analytics (leaderboard, top redeemers, BB distribution stats)
- Accept incoming BetterBucks transfers from employees via Apple/Google wallet tap (for internal reward redemption at org-run reward terminals)
- Configure tap-to-transfer settings (accepted memo types, transfer limits per employee)

### 3. EMPLOYEE
- Login → Employee Mobile Wallet Home
- View BetterBucks balance (displayed like a mobile wallet card — navy card, white text, kelly green accents)
- Transfer BetterBucks to org reward terminals via Apple/Google wallet tap gesture
- View full transaction history (BB received, BB spent, from/to, memo, timestamp)
- Receive push notifications for incoming BetterBucks awards
- View org-scoped leaderboard showing top BB earners

## TAP-TO-TRANSFER UX (APPLE/GOOGLE WALLET GESTURE)

This feature uses the device's native wallet tap UX purely as a gesture + biometric confirmation mechanism. No money is moved.

Flow:
1. Employee opens /employee/send, enters BB amount and selects recipient (or scans a QR code representing the org reward terminal)
2. App displays the Tap-to-Transfer screen: animated NFC ring, "BB [amount]" in large navy text, recipient name
3. User taps "Send with Apple Pay" or "Send with Google Pay" button
4. Device shows its native confirmation sheet (Face ID / Touch ID prompt) — if using Payment Request API, amount is $0.00 with label "BetterBucks Transfer"
5. On biometric success, frontend receives confirmation callback and immediately calls POST /api/wallets/transfer with a signed payload
6. Backend atomically debits sender and credits recipient in PostgreSQL, returns transaction_id and updated balances
7. App navigates to receipt screen: kelly green checkmark, "BB [amount] Sent", recipient name, transaction ID, timestamp, "Done" button

Org tap-to-accept terminal flow (for orgs running a reward redemption terminal):
1. Org opens /org/tap-to-pay on a dedicated device
2. Screen displays org name, a large QR code encoding the org's wallet recipient ID, and a live feed of incoming BB transfers
3. When employee scans and confirms transfer, org terminal screen animates a kelly green success state and logs the redemption

## DATABASE SCHEMA (Prisma)

Tables needed:
- User (id, email, passwordHash, role: ADMIN|ORG|EMPLOYEE, orgId?, createdAt)
- Organization (id, name, domain, status, bbPool, createdAt)
- Wallet (id, userId, balanceBB, createdAt, updatedAt)
- Transaction (id, senderId, recipientId, amountBB, type: AWARD|REDEMPTION|TRANSFER, memo, createdAt)
- ApiKey (id, orgId, keyHash, label, createdAt, revokedAt?)
- Webhook (id, orgId, url, events[], secret, createdAt)
- Notification (id, userId, message, read, createdAt)

No payment-related fields. No Stripe IDs. No fiat amounts anywhere in the schema.
